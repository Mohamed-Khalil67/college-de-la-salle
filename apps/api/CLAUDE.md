# apps/api — NestJS conventions

NestJS 12 (ESM), Prisma 7 with PostgreSQL 18, Vitest. Read the `nestjs-best-practices` skill before larger changes.

## Layout

- One **feature module** per folder under `src/` (`auth/`, `users/`, `classes/`, `events/`, `grades/`…): `x.module.ts`, `x.controller.ts`, `x.service.ts`, `dto/x.dto.ts`, and specs next to the code (`x.service.spec.ts`). Cross-cutting pieces live in `src/common/` (decorators, roles guard, pagination, dates, audit), permissions in `src/access/`, config in `src/config/`, the database client in `src/prisma/`.
- Import feature modules into `AppModule`. A module exports only what other modules need. No circular imports between modules.
- ESM: relative imports end in `.js` (`import { X } from './x.service.js'`).

## Contract, controllers, DTOs

- **The REST contract lives in `packages/shared/src/api.ts`** (request/response interfaces the web app imports). DTO classes `implements` those interfaces, so a contract change breaks the build until both sides follow. Add the interface there first.
- Controllers stay thin: parse the request, call a service, return a DTO. **No business logic or Prisma calls in controllers.**
- Every body, query and param is a DTO class validated with `class-validator` (global `ValidationPipe` with `whitelist`, `forbidNonWhitelisted`, `transform`). Never accept a raw object. Use `ParseUUIDPipe` for ids.
- Files named `*.dto.ts` are documented automatically by the Swagger CLI plugin (`nest-cli.json`); add `@ApiProperty` only for enums, nullable unions and nested arrays. A `/** comment */` on a route becomes its Swagger summary. Docs: `/api/docs` (JSON at `/api/docs-json`).
- Return response DTOs mapped from Prisma rows (`toXDto()`), never Prisma models (no `passwordHash` leaks). Decimals become `number`, `@db.Date` columns `YYYY-MM-DD` strings (`common/dates.ts`).
- Throw Nest HTTP exceptions from services (`forbidden()`, `notFound()` in `common/errors.ts`); messages are short French sentences shown to users.
- List endpoints that can grow are paginated with `PaginationQueryDto` + `paginated()` and documented with `@ApiPaginatedResponse(Dto)`.
- PATCH DTOs: class instances carry every declared field (unset ones as `undefined`), so drop undefined keys before merging with the current row.

## Auth and permissions

- Every route needs a Bearer access token (global `JwtAuthGuard`) unless marked `@Public()`. `@Roles('admin', …)` restricts by role (global `RolesGuard`); `@Roles('admin', 'planner')`, spelled `@StructureEditors()`, also lets in accounts the admin marked « Planificateur » (`User.isPlanner`, a permission on the account, not a role: teacher or admin accounts, never a student, which the API refuses with 400 and the `users_planner_not_student` CHECK refuses in the database). It is read from the database on every request, so a revoked planner is refused at once. Only the admin sets it (`PATCH /users/:id`), audited as `user.planner` (old and new value) in the same transaction; rows from before 12 Nov 2026 are `teacher.coordinator.grant`/`.revoke`. Only `isPlanner: true` is refused for a student (sending `false` is accepted). The grant gives exactly what the coordinator flag gave (structure writes, timetable, every group); nothing admin-only. Writes to the year's structure (subjects, class subjects, rooms, periods, calendar days, school years) use `@StructureEditors()` and nothing else: don't scatter role checks. `@CurrentUser()` gives the `AuthUser` (`id`, `role`, `studentId`, `teacherId`, `classId`, `isPlanner`).
- **Ownership is checked in services through `AccessService`** (`src/access/`), the API's version of `docs/legacy/firestore.rules`: students see their own records and the events/posts of their audience (`audienceFor`); teachers write grades, attendance and class events only where they have a `TeachingAssignment` on a `ClassSubject` of that class (`assertTeachesClass(user, classId, subjectId)`); a teacher's own activity types are private to them until the admin promotes them (`ActivityTypesService.usable()` hides other teachers' types); `assertCanReadStudent` for anything about one student. A role check alone is never enough.
- Refresh tokens: opaque, in the `cdls_refresh` httpOnly SameSite=Strict cookie (path `/api/auth`), stored as an HMAC, rotated on each refresh; reuse revokes the family. Deactivating a user or changing their password calls `AuthService.revokeAll`.
- **First sign-in:** `User.mustChangePassword` (set on every created, imported or reset account) closes every route except those marked `@AllowDuringPasswordChange()` (`/auth/me`, `POST /auth/password`; logout is public) with 403 `PASSWORD_CHANGE_REQUIRED`, in `JwtAuthGuard`. A password change or reset sets `passwordChangedAt`; access tokens carry that value as `pv` and are refused when it differs, so the other sessions end at once.
- `User.status` is `active | disabled | archived`; only `active` can sign in or refresh. Archived accounts are read-only (no edits, enrolment or requests until restored).
- Login e-mails are generated by `assignSchoolEmails` (`@cdls/shared`) with `SCHOOL_EMAIL_DOMAIN`; roster rows are checked by the pure `users/roster-import.ts`.
- Section changes (`section-changes/`): approval runs in ONE transaction (claim the request, close the open enrolment, open the new one, set `Student.sectionId`, audit row). Partial unique indexes (raw SQL in the schema, `partialIndexes` preview) keep one pending request per student and one open enrolment per student and year.
- Never log passwords, tokens or full request bodies. Hash passwords with `argon2`. Login and `POST /auth/password` are limited to 5 attempts a minute per address **and account** (`common/client-key.ts`: a class behind the school's one address must not share a counter; the `ip` throttler caps the address as a whole).
- Temporary passwords (created, imported or reset accounts) expire `TEMP_PASSWORD_TTL_DAYS` (default 14) after being set (`User.temporaryPasswordExpiresAt`): an expired one answers 401 « demandez-en un nouveau au secrétariat »; an admin reset restarts the clock, choosing a password clears it. Disabling, restoring or archiving an account bumps `passwordChangedAt`, so access tokens issued before are refused.
- **Forgotten password** (`auth/password-reset.service.ts`): public `POST /auth/forgot-password` always answers 204 (unknown, disabled and archived accounts get nothing; `request()` returns before it reads anything, and the lookup, the token row and the mail run after the answer, so timing and answer do not differ; a failure there is only logged) and is throttled per address and identifier (`forgotPasswordTracker`, plus the `ip` ceiling). The link token is 32 random bytes; only its HMAC is stored (`password_reset_tokens`, prefix `password-reset:`), single use (`usedAt`, claimed with `updateMany` in the transaction), `PASSWORD_RESET_TTL_MINUTES` long, and a new request deletes the account's earlier tokens. `POST /auth/reset-password` checks `passwordProblems` before spending the token, then sets the password, clears `mustChangePassword` and the temporary expiry, bumps `passwordChangedAt`, audits `user.password_reset_self` in the same transaction and calls `AuthService.revokeAll`. Never log tokens, links or passwords outside the dev `log` transport.
- **Mail** (`mail/`): `MailService` composes the French mails and calls a `MailTransport` (`MAIL_TRANSPORT` token): `LogMailTransport` (`MAIL_TRANSPORT=log`: API log + `apps/api/.dev-mail/`, gitignored; refused in production because it exposes links) or `SmtpMailTransport` (nodemailer; `MAIL_FROM`, `SMTP_*`). Links use `PUBLIC_WEB_URL`. e2e tests replace the transport with an in-memory list (`TestApp.mails`).
- **Audit sensitive account changes** in the same transaction: `user.create`, `user.password_reset`, `user.password_reset_self`, `user.status`, `user.import` (one row with counts: never passwords, tokens or lists of addresses), `user.planner`, `section_change.create`/`reject`/approve, `enrollment.close`. Unenrolling closes the enrolment (`leftOn`), it never deletes it.
- Roster import: a line is « déjà présent » (kept, skipped) when its student number exists, or, without a number, an account has the same exact normalised name (and section and class for students). A genuine homonym is created only through `createAnyway=<line,…>` in the request. Address numbering reads only the `prenom.nom%` addresses, under the e-mail advisory lock.

## Database (Prisma)

- Dev database: `npm run db:dev` (from the repo root) runs PostgreSQL 18 from npm (embedded-postgres) on port 5433, data in `apps/api/.dev-db/` (gitignored), and writes `DATABASE_URL` into `apps/api/.env`. The alternative is the system PostgreSQL 18 with the `cdls` role and `cdls_dev` database (`prisma/setup-database.sql`, run once by the user as `postgres`). Never ask for, guess or store the `postgres` superuser password, and never touch the system PostgreSQL service.
- Use `PrismaService` (global `PrismaModule`); never `new PrismaClient()` in app code. The client is generated into `src/generated/prisma` (gitignored): `npm run prisma:generate`.
- Schema changes go through migrations: edit `prisma/schema.prisma`, then `npm run db:migrate -- --name <change>`. **Never edit or rename a migration once any database applied it** (yours, another worktree's, the e2e one), even if it was never pushed: Prisma then reports drift or a checksum mismatch on every database that has the old version. Make a new migration instead. Each migration gets its own timestamp: `src/prisma/migrations.spec.ts` fails on two folders with the same one (the applied `20261112100000` pair is the only exception). Constraints Prisma can't express (CHECKs) go into the migration SQL (`--create-only`, edit, then migrate).
- **`prisma migrate reset` is refused for AI agents** (Prisma's own guard) and destroys data: don't run it or bypass the guard; ask the user. `npm run db:seed` wipes and re-seeds the dev database (fine for dev data; it regenerates the demo passwords in `demo-credentials.local.md`).
- snake_case tables and columns (`@@map` / `@map`), camelCase in TypeScript. Index every foreign key and common filter.
- Multi-step writes use `prisma.$transaction`. Avoid N+1 queries: `include`/`select` what you need.
- Grade changes write `AuditLog` rows in the same transaction (`common/audit.ts`).
- Pure domain logic (averages, calendar occurrences, audiences, .ics) lives in `packages/shared` and is imported from `@cdls/shared`, not re-implemented here. Activity types live in the database (`activity_types`): code asks for the flags (`gradable`, `repeatable`, `homework`), never for a type `code` such as `'cours'` or `'devoir'`; the system types come from `SYSTEM_ACTIVITY_TYPES` (seed and the `20261021000300` migration, checked by `src/prisma/activity-types.spec.ts`). Grades and report cards follow `Event.periodId`, never date ranges, so editing a period's dates moves no grade; a closed period is locked (`PeriodsService.assertOpen`). Subject coefficients live on `ClassSubject` and freeze once a period of the class's section is closed or has report cards (409); a planificateur who teaches the subject in that class cannot change its coefficient (admin only). The `periods_no_overlap` EXCLUDE only compares equal sections: the `periods_no_overlap_all_sections` trigger (same advisory lock as `PeriodsService.write`) also refuses an every-section period overlapping a section's. Events take a shared lock on their activity type (`lockForEvent`) so flag changes (exclusive lock) cannot race with event creation. `GET /calendar-days` needs a year or a range and shows students only what concerns their section and class. Holidays: `occurrences()` and `toIcs()` take the closures from `CalendarDaysService.closures()`.

## Quick grading (« Noter »)

- `grades/quick-grading.*`: `POST /grading/assessments` (teachers only) creates the gradable event in ONE transaction (today's `schoolToday()`, no time, the whole class (no target row), the period from `PeriodsService.resolveFor`, the type's shared lock) after `AccessService.assertTeachesClass`, audits `event.create` (`via: 'quick_grading'`), notifies nobody (students are told on publish), and answers `GradesService.sheet`. No open period covers today: 409 « Aucune période… »; closed: 409 « …clôturée ». The type is asked by flag (gradable, not homework; default: first gradable, non-homework, non-repeatable, in `sortOrder`), never by code. The scale (« Sur ») is not on the event: it travels with the marks (`SaveGradesRequest.outOf`, default 20). `GET /grading/pending` lists the class and subject's gradable events of open periods where a mark is missing or not yet visible (done = every student has a mark AND every mark is published), with `entered / total`; the 100-event cap applies after the finished ones are left out. A period closed between the lookup and the lock answers the same friendly 409.
- An absent student has no grade row: an empty mark is « absent, does not count » (the model has no absent status).

## Timetable

- `timetable/` (writes, reads, soft warnings) and `occupancy/` (the index). **Every write runs in one transaction** (`TimetableService.run`): save the slot or exception, clear and rebuild the `occupancy` rows of the slots it touches, detect hard conflicts (409 `TIMETABLE_CONFLICT`), compute soft warnings (409 `WARNINGS_NOT_ACKNOWLEDGED` unless `acknowledgedWarnings` carries a reason for each; reasons go to the audit log). `POST /timetable/check` is the same pipeline, rolled back. The exclusion constraints of `occupancy` are the last guard against two parallel requests (`OccupancyService.guard` turns their error into a 409). Queries inside a transaction run one after the other.
- **Suggestions on a conflict** (`timetable/suggestions.service.ts`, ranking in `packages/shared/src/suggestions.ts`): `TimetableService.run` asks `TimetableSuggestionsService.forConflicts` inside the same transaction, after the index was rebuilt, so the write's own old places count as free. The mutation says what to suggest (`Applied.suggest`: a session move or room change, or the series; nothing for a cancellation, restore or substitute, and no other room unless ONLY the room clashed). Candidates (periods learned from the year's own slots and kept inside `SCHOOL_DAY_HOURS`, holidays and days without classes removed, nothing before now) are built by the pure shared functions; the index is asked about ALL of them in one statement (`OccupancyService.clashingCandidates`, `EXISTS … OR EXISTS` with the indexes' `IS NOT NULL` predicates spelled out: a plain join made the planner hash-join the whole table, 170 ms against 8 ms for 600 rows) and the free rooms in one more (`roomsFreeDuring`). Cost on the seed (4,484 index rows): a series check with 600 to 1,100 candidate rows adds 25 to 55 ms to a 50 to 80 ms check; one session adds about 10 ms. Suggestions only carry ids, names and capacity of rooms and times: nothing about who holds them. A teacher reaches them only for a session of their own slot, because the mutation authorises before anything is suggested.
- The weekly rule is the source of truth; never edit `occupancy` by hand. Calendar days (`CalendarDaysService`) and one-off events (`EventsService`) call `OccupancyService` in their own transactions. Legacy weekly events are not indexed.
- « Aujourd'hui » is `schoolToday()` (Cairo, from `@cdls/shared`): sessions before it are never rewritten. Teachers change only `this` session of their own slots (cancel, move, room; no replacement); the series scopes are `@StructureEditors()` only.

## Planner page and « Professeur absent »

- `planner/` (`@StructureEditors()` on the whole controller: admin or planner, a teacher without the permission and a student get 403 on every route). Reads: `GET /planner/absence?teacherId&from&to` (the teacher's lessons, from today on, at most `ABSENCE_MAX_DAYS`, each with `freeTeachers`: active teachers with nothing in the `occupancy` index at that time, the ones who teach the subject first), `GET /planner/today?date` (exceptions of a day; a moved one is listed once, on the day it moved to, by `changeDay`, with `movedFrom`; `notified` = a notification of `entity: 'timetable_slot'` exists for a student), `GET /planner/rooms-now` (`OccupancyService.freeRoomIds` for this minute, `freeUntil` from the pure `freeUntil`), `GET /planner/timetables` (hours placed against `ClassSubject.hoursPerWeek` per class, pure `classCoverage` in `packages/shared/src/planner.ts`; parallel groups count once). `GET /timetable/warnings` without class, teacher or room is the whole school's (the page's « À régler »).
- **`POST /planner/absence` is `TimetableService.applyAbsence`**, not code of the planner module: one `Mutation` calls `writeException` for every choice (cancel, `substitute`, `study`) inside ONE `run` transaction, so the index, the hard conflicts (409 `TIMETABLE_CONFLICT`: nothing is written), the soft warnings (`Applied.onlySessions` limits them to the sessions written), the audit rows (`teacher_absence.apply` first, then one `slot_exception.upsert` per lesson) and the notifications commit or roll back together. A cover must be free (the index says it, not the preview, which is only advice) and have an active account (400 otherwise). Limits: `ABSENCE_MAX_DAYS` (14) and `ABSENCE_MAX_CHOICES` (60), both in `packages/shared/src/api.ts`; a request with 60 choices commits well inside the 20 s transaction timeout (e2e proves it). A substitute or study on a lesson whose exception is `moved` or `room_change` is refused with a French 400 (restore it first; cancelling is still allowed): covering it would silently undo that change. `GET /timetable/warnings` without a scope is capped at `SCHOOL_WARNINGS_MAX_DAYS` (31). `rooms-now` asks the index about the window from `probeWindow(time)`, never an empty one (an empty range overlaps nothing, so every room would read as free at 23:59).
- `SlotExceptionKind` `study` (supervised study): `newTeacherId` is the supervisor (required), `newRoomId` the room (optional, the lesson's own otherwise), no date or time change; `slot_exceptions_kind_check` says so (migration `20261112100000`, which compares `kind::text` because an enum value added in a migration cannot be used by name in the same transaction). The lesson stays on the class's timetable as `status: 'study'`; the supervisor holds the teacher index row and the absent teacher is free.
- Substituting or turning a lesson into a study notifies (`session_substituted`, `session_study`): the class, the lesson's teacher and the covering teacher; restoring any exception notifies, and a covering teacher whose session is taken away is told too (`SessionNotice.coverTeacherId` / `substituteTeacherId`). This holds for the single-exception endpoint too.

## Teacher summary

- `teacher-summary/`: `GET /teacher/summary` (`@Roles('teacher')`; admins and students get 403) is the teacher's home page in one read. It calls the services the detail pages use (`TimetableReadService.occurrences`, `CalendarDaysService.list`, `QuickGradingService.pending`, `EventsService.occurrences` with an `extra` where, `TargetsService.concernedIds`) so audiences and counts match, always scoped to the caller's `TeachingAssignment`s of the current year. The « Noter » section asks `QuickGradingService.pending` for each class and subject pair through `mapWithConcurrency` (`@cdls/shared`, `SUMMARY_PENDING_CONCURRENCY` = 4 at a time), never a parallel burst. Each section runs in its own try/catch: a failure is logged (message only) and named in `failed`. Pure rules (homework and tests windows, `repeatedAbsences`, `rollCallDone`, thresholds) are in `packages/shared/src/teacher-summary.ts`. Repeated absences count distinct days of `absent` (not `excused`, not `late`) in the class events of the teacher's classes over `REPEATED_ABSENCE_WINDOW_DAYS`. `attendance(recorded_by_id, date)` is indexed for « Appel fait ».

## Exams set by a planner (« Ajouter un examen »)

- No new endpoint: `POST /events` is `@Roles('teacher', 'admin')`; an admin account has no `Teacher` row, so `Event.authorId` is nullable and `Event.createdById` (a `User`, set on every new event; CHECK `events_has_author` says one of the two is set, migration `20261113000000`) is the author then. `authorName` reads the teacher's name, else the creator's. Never compare `authorId` with `teacherId` without checking it is not null (`editable()` does): « their own » is `authorId === teacherId` or `createdById === user.id`; the admin edits any.
- Authorization is `AccessService.assertCanSchedule(user, classId, subjectId, typeCode)`: `canSetForAnyClass` (`access/grants.ts`: admin or planner, and the type is one of `EXAM_ACTIVITY_CODES` in `@cdls/shared`) passes for any class, else `assertTeachesClass`. This is the one place that spells the exception: a planner still cannot set homework or a course for a class they do not teach, and a non-planner teacher or a student is refused for other classes (specs in `access.service.spec.ts`, `grants.spec.ts`, `test/planner-exams.e2e-spec.ts`).
- Clashes use the existing occupancy index (409 `TIMETABLE_CONFLICT`, nothing written); the soft « more than `MAX_ASSESSMENTS_PER_DAY` assessments » rule is advice in the web form, not enforced here. Creation, change and deletion of an exam through that grant write `event.exam.create|update|delete` audit rows in the same transaction (a teacher's own events are not audited, as before).
- **Write-time re-check and the author-less account.** `EventsService.editable()` (update and delete) applies `assertCanSchedule` for the stored event's class, subject and type after the ownership test: a planner whose permission was revoked, or a teacher no longer assigned to the class (who then cannot delete their own old homework either: the admin does it), keeps the event but gets 403 on `PATCH`/`DELETE`, with no audit row (the admin still passes). Only events bound to a class are re-checked: a section-wide or school-wide event has no class to authorise, so it stays with its author, as at creation. An account with no teacher profile (the admin without a `Teacher` row) may create only exam types: any other type, class-bound or school-wide, is refused with 403 « Ce compte n’a pas de profil enseignant… », because such an event would have no author name and no audit (`check()` in `events.service.ts`, also when an update changes the type to a non-exam one). No existing admin screen or test created non-exam events through `POST /events` (the web event form is in the teacher space), so nothing legitimate depends on the old behaviour; an admin who also has a teacher profile still creates every kind, as that teacher. An admin editing or deleting someone else's non-exam event is the existing moderation path and stays unaudited, as before. `auditExam` also writes the row when the exam grant applied to the event before the change (an exam turned into another type).
- A mark or a roll call is recorded under `AccessService.recorderFor` (the signed-in teacher, else the event's teacher, else a teacher of the class and subject, else 409 « Aucun enseignant… »), because `Grade.gradedById` and `Attendance.recordedById` are teachers.

## Groups and targets

- `groups/` (CRUD, members, `GET /groups/mine`) and `targets/` (`TargetsService`, the ONE place that says which students a piece of work concerns, from `targetedStudentIds` in `@cdls/shared`). Every group route loads the group and authorises on ITS class (`GroupsService.authorize`); never trust a class id the caller sends for a group id. Memberships are soft (`leftOn`); take a student out of a class only through code that also calls `closeGroupMemberships` in the same transaction.
- Events with a class and a gradable or homework type carry `AssessmentTarget` rows (no row = whole class). Grade and attendance writes lock the event row (`FOR UPDATE`) and re-resolve the targets inside the transaction. Lists for students use `AccessService.eventAudienceFor` (`concernsStudentNow`), not `audienceFor`. Grades are never deleted by an audience change (409).
- A timetable slot with `groupId` takes its `division` from the group; the occupancy index carries `group_id` (`occupancy_group_no_overlap`). A timed one-off event for exactly one group holds that group's division of the class (`occupancy/event-hold.ts`); for several groups, students or the whole class it holds the whole class.

## Rollover and archived years

- `rollover/`: `plan.ts` is pure (snapshot + request → plan, hash); `RolloverService` runs the plan in one transaction, a preview rolls it back, an apply compares the hash (409 `ROLLOVER_PREVIEW_STALE`). Match natural keys so re-runs create nothing; write the new year through `tx` (not the services that open their own transactions). Other modules plug steps in through `ROLLOVER_EXTRA_STEPS` (`rollover-step.ts`). The groups plug in that way (`groups-rollover-step.ts`: groups copied empty, memberships only for promoted students, sessions of groups); new slots are always placed through `placeNewSlots` (`slot-placement.ts`), never one query round per slot.
- An archived year (`school_years.archived_at`) is read-only: call `assertClassWritable(tx, classId)` or `assertYearIdWritable(tx, yearId)` (`school-years/year-guard.ts`) at the start of every write into a year's classes, enrolments, subjects, periods, calendar, grades, attendance, events or timetable. They take a SHARE lock that the archive's exclusive lock waits for. Group writes and the « Assigner à » of events are covered the same way.

## Calendar feed and notifications

- `calendar-feed/`: one secret feed address per student or teacher (`calendar_feeds`, one row per user). The token is the row id (32 hex digits) plus a 43-character random secret; only `HMAC-SHA256(JWT_REFRESH_SECRET, "calendar-feed:" + secret)` is stored, compared with `timingSafeEqual`, and the same hashing work is done for a malformed token. Every refusal (malformed, unknown id, wrong secret, revoked, replaced, inactive account, password changed since) is the same 404 « Agenda introuvable. ». The row copies the account's `passwordChangedAt` as `passwordVersion`: a password change or reset, disabling, restoring or archiving bump it, so old links die without a hook in those services. `POST` replaces the row (new id) and writes a `calendar_feed.create` audit row, `DELETE` a `calendar_feed.revoke` one: never the token, in the audit rows or the log. The public route is `@Public()`, throttled by `FEED_THROTTLE_LIMIT`, and answers `private, no-store`, `no-referrer`, `noindex`; the web container's nginx keeps `/api/calendar/feed/` out of its access log (the address is the credential).
- `FeedBuilderService` is the ONLY place that decides what a feed shows. Students: the current class (`AccessService.placement`), whole-class sessions and those of their groups, the events of `AccessService.eventAudienceFor`, the calendar days of their section and class. Teachers: their slots of the current year (substitutions included, as taught now), events they wrote or that concern the classes and subjects they teach, the days of their sections and classes. Cancelled sessions and the trace of a moved one are left out; a moved session keeps the UID of its original day. The text comes from the pure `packages/shared/src/feed.ts` (VTIMEZONE, folding, escaping, UIDs, SEQUENCE in seconds since 2026 from `updatedAt`): never build ICS lines in the API.
- `notifications/`: `NotificationsService.write(tx, drafts, actorId)` inserts the rows inside the CALLER'S transaction; `ChangeNoticesService` (exported) resolves the audience (class roster, group members, `TargetsService.concernedIds`, the event's author, the slot's teacher) and is called by `TimetableService.run` (exceptions and restores, after the conflict checks, never on a dry run), `EventsService` (homework created, event moved or re-roomed, event deleted) and `GradesService` (grades published, late grades of a published event). The actor never notifies themself; only `active` accounts receive. Texts are French and come from `packages/shared/src/notifications.ts`. A new kind goes in the shared `NOTIFICATION_KINDS`, the Prisma enum (new migration) and the shared spec.
- **Report preparation and « Relancer »** (`report-cards/report-preparation.*`, `report-gaps.ts` pure with a spec): `GET /periods/:id/report-preparation` (admin only, any period) says per class which subjects are not ready for the report cards: `no_grades` (no mark on any gradable event of the period), `incomplete` (an event of the whole class lacks marks, or an event has none; events aimed at some students are only checked for having marks), `unpublished` (all entered, some hidden), with the teachers of that class subject. `POST /periods/:id/report-preparation/reminders` (admin only, `REMINDER_THROTTLE_LIMIT` a minute, default 10) writes one `grades_reminder` notification per teacher with something to finish (link `/enseignant/notes`, text from `gradesReminderNotice`), only on an open period (409 otherwise). One reminder per teacher every `GRADE_REMINDER_COOLDOWN_HOURS` (12), per scope (a class reminder is keyed on the class, a whole-period one on the period and also covers its classes; the notification's `entity` is `class` or `period`); work not held yet (a gradable event dated after today with no mark) is not waited for, and marks of students no longer enrolled do not stand in for a missing one: the check, the notifications and the `report_preparation.remind` audit row (counts only, no names) share one transaction and one advisory lock, so a double click cannot send twice. A whole-period reminder also waits for an earlier reminder about any class of the period. The period is read again `FOR SHARE` inside the transaction, so a term closed meanwhile is refused (409). Only active teacher accounts are listed in a gap or counted in `teachers` / `lateTeacherCount`; a disabled or archived one is counted apart as `unreachable`, so `teachers = notified + alreadyReminded`. The answer counts `teachers`, `notified`, `alreadyReminded`, `unreachable` and `withoutTeacher` (subjects nobody teaches, or only taught by an inactive account). `GET /users` also filters on `isPlanner` and `mustChangePassword` (partial indexes) for the admin page.
- E-mail copies: `User.notifyByEmail` (default false). `NotificationMailService` (timer every `NOTIFICATION_MAIL_INTERVAL_MINUTES`, plus a daily retention purge) skips (`mail_state = 'skipped'`) notifications whose day is past, that were read, older than a day, or whose user opted out; the rest is claimed (`pending` → `sent` in one `updateMany`) before one grouped mail per user, and handed back when the send fails. e2e tests call `sendDigests()` / `purge()` directly.

## Type safety

- `tsconfig.json` is strict plus `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noUnusedLocals`, `noUnusedParameters` and `verbatimModuleSyntax` (type-only imports are `import type`). `array[i]` is `T | undefined`: narrow it. `strictPropertyInitialization` stays off for DTO classes, and `exactOptionalPropertyTypes` is not on (27 errors, mostly Prisma input types).
- No `any`, no `as unknown as` outside specs. A `Json` column is read with `readJsonList(value, guard)` and a type guard (`common/json.ts`), never a cast: see `isAttachment` (`events/event.mapper.ts`) and `isCardSubject` (`report-cards/report-cards.service.ts`).
- Unused constructor parameters are removed, not kept "for later": an injected service that is never read is a dependency the module graph pays for.
- Prisma error codes go through `common/errors.ts` (`isUniqueViolation`, `isForeignKeyViolation`, `conflictOnUnique`, `conflictOnReference`); do not re-declare them in a service.

## Config

- All environment variables are declared and validated in `src/config/env.validation.ts`; add new ones there and to `.env.example` (placeholders only, never real secrets). Read them with `ConfigService<Env, true>`.
- Roster imports have their own limit, `IMPORT_THROTTLE_LIMIT` (10 a minute, preview twice that); repeated e2e runs of the import tests need it raised.
- The one exception is a `@Throttle()` limit, which is evaluated where nothing is injected: use `throttleLimit('NAME')` (`config/throttle-limits.ts`), which reads the environment per request and takes its default from `Env`. Never write `process.env[...]` or a second default in a controller.

## Deployment (Docker)

- `Dockerfile` here, the stack in `deploy/` (`docs/deployment.md`). The image runs `prisma migrate deploy` in `docker-entrypoint.sh`, then `node dist/main.js`, as the non-root `node` user, with a healthcheck on `/api/health`. `prisma`, `tsx` and `dotenv` are regular dependencies because the image needs them (migrations, `seed:demo`).
- A fresh production database has no admin and no sections or subjects: `src/cli/create-admin.ts` (`node dist/cli/create-admin.js --email … --first … --last … [--reset]`) creates the first admin (temporary password, change forced) and upserts the reference data. Never use `db:seed` on a real database: it wipes it.
- `COOKIE_SECURE` (optional) overrides the refresh cookie's `Secure` flag, which defaults to `NODE_ENV === 'production'`. Behind the web container's nginx, `TRUST_PROXY=1`.

## Tests

- Unit tests (`src/**/*.spec.ts`) use the Nest testing module (`Test.createTestingModule`) and mock `PrismaService` and other services with `vi.fn()`. Keep pure computations (e.g. `report-cards/compute.ts`) in plain functions and test them directly.
- e2e tests (`test/*.e2e-spec.ts`) need the dev database server running. Each run creates its own throwaway database (`cdls_e2e_<random>`), applies migrations with `prisma migrate deploy`, seeds it with one random password, and drops it at the end (`test/global-setup.ts`). Use `createTestApp()` from `test/helpers.ts`; it logs in once per account because login is rate-limited (5 per minute per app).
- Every permission rule gets an e2e test (see `test/permissions.e2e-spec.ts`).
- **The specs share one database and run one after the other, so each leaves it as it found it.** Fixture accounts get `UNUSABLE_PASSWORD_HASH` (`test/helpers.ts`, a well-formed argon2 hash nobody can sign in with), never `'x'`; fixtures that create users, classes or a year have a matching cleanup (`deleteUsers`, `removeRolloverSource`) run in `afterAll`/`finally`. Never pick « some student » with an unordered `findFirst`: use `studentOf()` (a seeded student, by e-mail) or filter on `studentNumber: { startsWith: 'CDLS-' }`. Count or read only what your own requests made (`createdAt >= start of the spec`), and delete the notifications and exceptions you cause: rows from earlier specs about the same demo students and slots are still there. Timed moves in tests go on a Friday evening (the school week is Sunday to Thursday), so they cannot clash with the demo timetable.
- `AuthService` treats a stored hash that argon2 cannot parse as a wrong password (401), never a 500.
- `npm test` (unit), `npm run test:e2e`, `npm run lint` (oxlint, type-aware) must pass before a PR.
