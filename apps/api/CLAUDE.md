# apps/api — NestJS conventions

NestJS 12 (ESM), Prisma 7 with PostgreSQL 18, Vitest. Read the `nestjs-best-practices` skill before larger changes.

## Layout

- One **feature module** per folder under `src/` (`auth/`, `users/`, `classes/`, `events/`, `grades/`…): `x.module.ts`, `x.controller.ts`, `x.service.ts`, `dto/x.dto.ts`, and specs next to the code (`x.service.spec.ts`). Cross-cutting pieces live in `src/common/` (decorators, roles guard, pagination, dates, audit), permissions in `src/access/`, config in `src/config/`, the database client in `src/prisma/`.
- Import feature modules into `AppModule`. A module exports only what other modules need. No circular imports between modules.
- ESM: relative imports end in `.js` (`import { X } from './x.service.js'`).

## Contract, controllers, DTOs

- **The REST contract lives in `packages/shared/src/api.ts`** (request/response interfaces the web app imports). DTO classes `implements` those interfaces, so a contract change breaks the build until both sides follow. Add the interface there first.
- Controllers stay thin: parse the request, call a service, return a DTO. **No business logic or Prisma calls in controllers.**
- Every body, query and param is a DTO class validated with `class-validator` (global `ValidationPipe` with `whitelist`, `forbidNonWhitelisted`, `transform`). Never accept a raw object. Use `ParseUUIDPipe` for ids.
- Files named `*.dto.ts` are documented automatically by the Swagger CLI plugin (`nest-cli.json`); add `@ApiProperty` only for enums, nullable unions and nested arrays. A `/** comment */` on a route becomes its Swagger summary. Docs: `/api/docs` (JSON at `/api/docs-json`).
- Return response DTOs mapped from Prisma rows (`toXDto()`), never Prisma models (no `passwordHash` leaks). Decimals become `number`, `@db.Date` columns `YYYY-MM-DD` strings (`common/dates.ts`).
- Throw Nest HTTP exceptions from services (`forbidden()`, `notFound()` in `common/errors.ts`); messages are short French sentences shown to users.
- List endpoints that can grow are paginated with `PaginationQueryDto` + `paginated()` and documented with `@ApiPaginatedResponse(Dto)`.
- PATCH DTOs: class instances carry every declared field (unset ones as `undefined`), so drop undefined keys before merging with the current row.

## Auth and permissions

- Every route needs a Bearer access token (global `JwtAuthGuard`) unless marked `@Public()`. `@Roles('admin', …)` restricts by role (global `RolesGuard`); `@Roles('admin', 'coordinator')`, spelled `@StructureEditors()`, also lets in teachers the admin marked `isCoordinator` (read from the database on every request, so a revoked coordinator is refused at once). Writes to the year's structure (subjects, class subjects, rooms, periods, calendar days, school years) use `@StructureEditors()` and nothing else: don't scatter role checks. `@CurrentUser()` gives the `AuthUser` (`id`, `role`, `studentId`, `teacherId`, `classId`, `isCoordinator`).
- **Ownership is checked in services through `AccessService`** (`src/access/`), the API's version of `docs/legacy/firestore.rules`: students see their own records and the events/posts of their audience (`audienceFor`); teachers write grades, attendance and class events only where they have a `TeachingAssignment` on a `ClassSubject` of that class (`assertTeachesClass(user, classId, subjectId)`); a teacher's own activity types are private to them until the admin promotes them (`ActivityTypesService.usable()` hides other teachers' types); `assertCanReadStudent` for anything about one student. A role check alone is never enough.
- Refresh tokens: opaque, in the `cdls_refresh` httpOnly SameSite=Strict cookie (path `/api/auth`), stored as an HMAC, rotated on each refresh; reuse revokes the family. Deactivating a user or changing their password calls `AuthService.revokeAll`.
- **First sign-in:** `User.mustChangePassword` (set on every created, imported or reset account) closes every route except those marked `@AllowDuringPasswordChange()` (`/auth/me`, `POST /auth/password`; logout is public) with 403 `PASSWORD_CHANGE_REQUIRED`, in `JwtAuthGuard`. A password change or reset sets `passwordChangedAt`; access tokens carry that value as `pv` and are refused when it differs, so the other sessions end at once.
- `User.status` is `active | disabled | archived`; only `active` can sign in or refresh. Archived accounts are read-only (no edits, enrolment or requests until restored).
- Login e-mails are generated by `assignSchoolEmails` (`@cdls/shared`) with `SCHOOL_EMAIL_DOMAIN`; roster rows are checked by the pure `users/roster-import.ts`.
- Section changes (`section-changes/`): approval runs in ONE transaction (claim the request, close the open enrolment, open the new one, set `Student.sectionId`, audit row). Partial unique indexes (raw SQL in the schema, `partialIndexes` preview) keep one pending request per student and one open enrolment per student and year.
- Never log passwords, tokens or full request bodies. Hash passwords with `argon2`. Login and `POST /auth/password` are limited to 5 attempts a minute per address **and account** (`common/client-key.ts`: a class behind the school's one address must not share a counter; the `ip` throttler caps the address as a whole).
- Temporary passwords (created, imported or reset accounts) expire `TEMP_PASSWORD_TTL_DAYS` (default 14) after being set (`User.temporaryPasswordExpiresAt`): an expired one answers 401 « demandez-en un nouveau au secrétariat »; an admin reset restarts the clock, choosing a password clears it. Disabling, restoring or archiving an account bumps `passwordChangedAt`, so access tokens issued before are refused.
- **Forgotten password** (`auth/password-reset.service.ts`): public `POST /auth/forgot-password` always answers 204 (unknown, disabled and archived accounts get nothing; the mail is sent in the background so timing and answer do not differ) and is throttled per address and identifier (`forgotPasswordTracker`, plus the `ip` ceiling). The link token is 32 random bytes; only its HMAC is stored (`password_reset_tokens`, prefix `password-reset:`), single use (`usedAt`, claimed with `updateMany` in the transaction), `PASSWORD_RESET_TTL_MINUTES` long, and a new request deletes the account's earlier tokens. `POST /auth/reset-password` checks `passwordProblems` before spending the token, then sets the password, clears `mustChangePassword` and the temporary expiry, bumps `passwordChangedAt`, audits `user.password_reset_self` in the same transaction and calls `AuthService.revokeAll`. Never log tokens, links or passwords outside the dev `log` transport.
- **Mail** (`mail/`): `MailService` composes the French mails and calls a `MailTransport` (`MAIL_TRANSPORT` token): `LogMailTransport` (`MAIL_TRANSPORT=log`: API log + `apps/api/.dev-mail/`, gitignored; refused in production because it exposes links) or `SmtpMailTransport` (nodemailer; `MAIL_FROM`, `SMTP_*`). Links use `PUBLIC_WEB_URL`. e2e tests replace the transport with an in-memory list (`TestApp.mails`).
- **Audit sensitive account changes** in the same transaction: `user.create`, `user.password_reset`, `user.password_reset_self`, `user.status`, `user.import` (one row with counts: never passwords, tokens or lists of addresses), `section_change.create`/`reject`/approve, `enrollment.close`. Unenrolling closes the enrolment (`leftOn`), it never deletes it.
- Roster import: a line is « déjà présent » (kept, skipped) when its student number exists, or, without a number, an account has the same exact normalised name (and section and class for students). A genuine homonym is created only through `createAnyway=<line,…>` in the request. Address numbering reads only the `prenom.nom%` addresses, under the e-mail advisory lock.

## Database (Prisma)

- Dev database: `npm run db:dev` (from the repo root) runs PostgreSQL 18 from npm (embedded-postgres) on port 5433, data in `apps/api/.dev-db/` (gitignored), and writes `DATABASE_URL` into `apps/api/.env`. The alternative is the system PostgreSQL 18 with the `cdls` role and `cdls_dev` database (`prisma/setup-database.sql`, run once by the user as `postgres`). Never ask for, guess or store the `postgres` superuser password, and never touch the system PostgreSQL service.
- Use `PrismaService` (global `PrismaModule`); never `new PrismaClient()` in app code. The client is generated into `src/generated/prisma` (gitignored): `npm run prisma:generate`.
- Schema changes go through migrations: edit `prisma/schema.prisma`, then `npm run db:migrate -- --name <change>`. Never edit an applied migration. Constraints Prisma can't express (CHECKs) go into the migration SQL (`--create-only`, edit, then migrate).
- **`prisma migrate reset` is refused for AI agents** (Prisma's own guard) and destroys data: don't run it or bypass the guard; ask the user. `npm run db:seed` wipes and re-seeds the dev database (fine for dev data; it regenerates the demo passwords in `demo-credentials.local.md`).
- snake_case tables and columns (`@@map` / `@map`), camelCase in TypeScript. Index every foreign key and common filter.
- Multi-step writes use `prisma.$transaction`. Avoid N+1 queries: `include`/`select` what you need.
- Grade changes write `AuditLog` rows in the same transaction (`common/audit.ts`).
- Pure domain logic (averages, calendar occurrences, audiences, .ics) lives in `packages/shared` and is imported from `@cdls/shared`, not re-implemented here. Activity types live in the database (`activity_types`): code asks for the flags (`gradable`, `repeatable`, `homework`), never for a type `code` such as `'cours'` or `'devoir'`; the system types come from `SYSTEM_ACTIVITY_TYPES` (seed and the `20261021000300` migration, checked by `src/prisma/activity-types.spec.ts`). Grades and report cards follow `Event.periodId`, never date ranges, so editing a period's dates moves no grade; a closed period is locked (`PeriodsService.assertOpen`). Subject coefficients live on `ClassSubject` and freeze once a period of the class's section is closed or has report cards (409); a coordinator cannot change one for a subject they teach themself (admin only). The `periods_no_overlap` EXCLUDE only compares equal sections: the `periods_no_overlap_all_sections` trigger (same advisory lock as `PeriodsService.write`) also refuses an every-section period overlapping a section's. Events take a shared lock on their activity type (`lockForEvent`) so flag changes (exclusive lock) cannot race with event creation. `GET /calendar-days` needs a year or a range and shows students only what concerns their section and class. Holidays: `occurrences()` and `toIcs()` take the closures from `CalendarDaysService.closures()`.

## Timetable

- `timetable/` (writes, reads, soft warnings) and `occupancy/` (the index). **Every write runs in one transaction** (`TimetableService.run`): save the slot or exception, clear and rebuild the `occupancy` rows of the slots it touches, detect hard conflicts (409 `TIMETABLE_CONFLICT`), compute soft warnings (409 `WARNINGS_NOT_ACKNOWLEDGED` unless `acknowledgedWarnings` carries a reason for each; reasons go to the audit log). `POST /timetable/check` is the same pipeline, rolled back. The exclusion constraints of `occupancy` are the last guard against two parallel requests (`OccupancyService.guard` turns their error into a 409). Queries inside a transaction run one after the other.
- **Suggestions on a conflict** (`timetable/suggestions.service.ts`, ranking in `packages/shared/src/suggestions.ts`): `TimetableService.run` asks `TimetableSuggestionsService.forConflicts` inside the same transaction, after the index was rebuilt, so the write's own old places count as free. The mutation says what to suggest (`Applied.suggest`: a session move or room change, or the series; nothing for a cancellation, restore or substitute, and no other room unless ONLY the room clashed). Candidates (periods learned from the year's own slots and kept inside `SCHOOL_DAY_HOURS`, holidays and days without classes removed, nothing before now) are built by the pure shared functions; the index is asked about ALL of them in one statement (`OccupancyService.clashingCandidates`, `EXISTS … OR EXISTS` with the indexes' `IS NOT NULL` predicates spelled out: a plain join made the planner hash-join the whole table, 170 ms against 8 ms for 600 rows) and the free rooms in one more (`roomsFreeDuring`). Cost on the seed (4,484 index rows): a series check with 600 to 1,100 candidate rows adds 25 to 55 ms to a 50 to 80 ms check; one session adds about 10 ms. Suggestions only carry ids, names and capacity of rooms and times: nothing about who holds them. A teacher reaches them only for a session of their own slot, because the mutation authorises before anything is suggested.
- The weekly rule is the source of truth; never edit `occupancy` by hand. Calendar days (`CalendarDaysService`) and one-off events (`EventsService`) call `OccupancyService` in their own transactions. Legacy weekly events are not indexed.
- « Aujourd'hui » is `schoolToday()` (Cairo, from `@cdls/shared`): sessions before it are never rewritten. Teachers change only `this` session of their own slots (cancel, move, room; no replacement); the series scopes are `@StructureEditors()` only.

## Groups and targets

- `groups/` (CRUD, members, `GET /groups/mine`) and `targets/` (`TargetsService`, the ONE place that says which students a piece of work concerns, from `targetedStudentIds` in `@cdls/shared`). Every group route loads the group and authorises on ITS class (`GroupsService.authorize`); never trust a class id the caller sends for a group id. Memberships are soft (`leftOn`); take a student out of a class only through code that also calls `closeGroupMemberships` in the same transaction.
- Events with a class and a gradable or homework type carry `AssessmentTarget` rows (no row = whole class). Grade and attendance writes lock the event row (`FOR UPDATE`) and re-resolve the targets inside the transaction. Lists for students use `AccessService.eventAudienceFor` (`concernsStudentNow`), not `audienceFor`. Grades are never deleted by an audience change (409).
- A timetable slot with `groupId` takes its `division` from the group; the occupancy index carries `group_id` (`occupancy_group_no_overlap`). A timed one-off event for exactly one group holds that group's division of the class (`occupancy/event-hold.ts`); for several groups, students or the whole class it holds the whole class.

## Rollover and archived years

- `rollover/`: `plan.ts` is pure (snapshot + request → plan, hash); `RolloverService` runs the plan in one transaction, a preview rolls it back, an apply compares the hash (409 `ROLLOVER_PREVIEW_STALE`). Match natural keys so re-runs create nothing; write the new year through `tx` (not the services that open their own transactions). Other modules plug steps in through `ROLLOVER_EXTRA_STEPS` (`rollover-step.ts`). The groups plug in that way (`groups-rollover-step.ts`: groups copied empty, memberships only for promoted students, sessions of groups); new slots are always placed through `placeNewSlots` (`slot-placement.ts`), never one query round per slot.
- An archived year (`school_years.archived_at`) is read-only: call `assertClassWritable(tx, classId)` or `assertYearIdWritable(tx, yearId)` (`school-years/year-guard.ts`) at the start of every write into a year's classes, enrolments, subjects, periods, calendar, grades, attendance, events or timetable. They take a SHARE lock that the archive's exclusive lock waits for. Group writes and the « Assigner à » of events are covered the same way.

## Config

- All environment variables are declared and validated in `src/config/env.validation.ts`; add new ones there and to `.env.example` (placeholders only, never real secrets). Read them with `ConfigService<Env, true>`.

## Deployment (Docker)

- `Dockerfile` here, the stack in `deploy/` (`docs/deployment.md`). The image runs `prisma migrate deploy` in `docker-entrypoint.sh`, then `node dist/main.js`, as the non-root `node` user, with a healthcheck on `/api/health`. `prisma`, `tsx` and `dotenv` are regular dependencies because the image needs them (migrations, `seed:demo`).
- A fresh production database has no admin and no sections or subjects: `src/cli/create-admin.ts` (`node dist/cli/create-admin.js --email … --first … --last … [--reset]`) creates the first admin (temporary password, change forced) and upserts the reference data. Never use `db:seed` on a real database: it wipes it.
- `COOKIE_SECURE` (optional) overrides the refresh cookie's `Secure` flag, which defaults to `NODE_ENV === 'production'`. Behind the web container's nginx, `TRUST_PROXY=1`.

## Tests

- Unit tests (`src/**/*.spec.ts`) use the Nest testing module (`Test.createTestingModule`) and mock `PrismaService` and other services with `vi.fn()`. Keep pure computations (e.g. `report-cards/compute.ts`) in plain functions and test them directly.
- e2e tests (`test/*.e2e-spec.ts`) need the dev database server running. Each run creates its own throwaway database (`cdls_e2e_<random>`), applies migrations with `prisma migrate deploy`, seeds it with one random password, and drops it at the end (`test/global-setup.ts`). Use `createTestApp()` from `test/helpers.ts`; it logs in once per account because login is rate-limited (5 per minute per app).
- Every permission rule gets an e2e test (see `test/permissions.e2e-spec.ts`).
- `npm test` (unit), `npm run test:e2e`, `npm run lint` (oxlint, type-aware) must pass before a PR.
